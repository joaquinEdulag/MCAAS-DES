Idea central: la base origen nunca necesita conocer los destinos. MCAAS - DES lee mediante un SELECT, identifica cambios localmente y replica cada cambio hacia los destinos configurados de forma independiente.

1. Objetivo y alcance

MCAAS - DES unifica dos responsabilidades: extracción y envío. Su propósito es ejecutar una consulta SQL configurable contra una base de datos origen, convertir el resultado en operaciones de escritura seguras y replicarlas hacia una o varias bases de datos externas.

El sistema no está acoplado a CONTPAQi. CONTPAQi es un caso de uso natural porque normalmente expone información en SQL Server, pero el origen puede ser SQL Server, PostgreSQL o MySQL siempre que se proporcionen credenciales válidas y conectividad de red.

1-10destinos por instalación

24/7operación prevista

La sincronización es cercana a tiempo real mediante polling. Por defecto se espera 2 segundos entre ciclos completos, pero el valor es configurable en POLL_INTERVAL_MS.

2. Arquitectura y flujo

BASE ORIGEN
SQL Server / PostgreSQL / MySQL
  |
  | EXTRACTION_SCRIPT
  v
SELECT -> Validación -> Hash de clave + Hash de fila -> Estado local por destino
  |
  +--> Destino 1 -> INSERT/UPDATE -> espera 300 ms
  +--> Destino 2 -> INSERT/UPDATE -> espera 300 ms
  +--> Destino 3 -> INSERT/UPDATE -> espera 300 ms
  +--> ... hasta Destino 10

3. Funciones soportadas

  • Extracción dinámica mediante un archivo .sql.
  • Origen SQL Server, PostgreSQL o MySQL.
  • Entre 1 y 10 destinos, cada uno con credenciales y política histórica independientes.
  • Conexión por URL o por host, puerto, base, usuario y contraseña.
  • TLS/SSL y certificado CA opcional para PostgreSQL/MySQL.
  • Tabla destino definida en el script, con sobrescritura opcional por destino.
  • Detección de filas nuevas y filas modificadas.
  • Modo normal: UPDATE por clave; si no existe, INSERT.
  • Modo histórico: INSERT de una nueva versión cada vez que cambia una fila.
  • Batches transaccionales configurables.
  • Logs sin almacenar el contenido de las filas en el archivo de banderas.
  • Alertas por Gmail API con OAuth 2.0.
  • Comandos de diagnóstico sin levantar el servicio permanentemente.
  • Build Windows autocontenido para PC sin Node.js.
No crea tablas automáticamente. Las tablas de destino deben existir antes del lanzamiento y sus columnas deben ser compatibles con el resultado del SELECT.

4. Requisitos pre-lanzamiento

4.1 Base origen

  • Servidor accesible desde la PC donde correrá MCAAS - DES.
  • TCP/IP habilitado cuando el motor lo requiera. En SQL Server esto suele ser relevante.
  • Usuario dedicado de solo lectura.
  • Permiso SELECT sobre todas las tablas/vistas usadas por el script.
  • Una combinación de columnas estable y no nula para usar como MCAAS_KEY_COLUMNS.

4.2 Bases destino

  • Tabla destino creada.
  • Columnas compatibles por nombre y tipo con el SELECT.
  • Usuario con permisos INSERT y UPDATE en destinos normales.
  • Usuario con permiso INSERT en destinos históricos.
  • Reglas de firewall y puertos abiertos desde el servidor MCAAS.
  • TLS/CA configurado si el proveedor, como Aiven, lo exige.

4.3 Máquina de compilación

Solo la máquina que compila necesita Node.js y npm. Se recomienda Node 22 o superior para el pipeline incluido. El servidor que recibe el build no necesita Node.js.

4.4 Servidor de operación

Windows x64, permisos de Administrador durante la instalación, conectividad a todas las bases y espacio para logs/estado. La aplicación se registra mediante Task Scheduler.

Para un servidor de renta con CONTPAQi: no se requiere instalar herramientas de desarrollo. Compile en otra PC, copie la carpeta de release y ejecute el instalador PowerShell como Administrador.

7. Script SQL dinámico

El script SQL es el contrato de extracción. Puede sustituirse sin recompilar. Debe devolver un conjunto tabular y declarar la tabla destino y las columnas que identifican de forma única cada fila.

-- MCAAS_NAME=Clientes
-- MCAAS_TARGET_TABLE=clientes
-- MCAAS_KEY_COLUMNS=IdCliente,EmpresaId

SELECT
    IdCliente,
    EmpresaId,
    Nombre,
    RFC,
    FechaModificacion
FROM dbo.Clientes;

Cómo se convierte el resultado

Si el SELECT devuelve las columnas IdCliente, Nombre y FechaModificacion, el sender genera operaciones equivalentes a:

INSERT INTO clientes (IdCliente, Nombre, FechaModificacion)
VALUES (?, ?, ?);

Los valores reales se envían como parámetros del driver. Esto evita problemas de comillas, tipos de datos y concatenación insegura.

Clave obligatoria: las columnas indicadas en MCAAS_KEY_COLUMNS deben estar presentes en el SELECT, no pueden ser NULL y la combinación debe ser única dentro del resultado.

8. Detección de filas nuevas y actualizadas

Para cada fila se calculan dos huellas:

  1. Key hash: SHA-256 de las columnas clave. Identifica la entidad sin guardar su valor en el log de banderas.
  2. Data hash: SHA-256 de toda la fila normalizada. Permite saber si cambió cualquier columna seleccionada.

El estado se guarda por stream y por destino en state/sync-state.json. Por eso, si Producción sincroniza y Shadow falla, únicamente Producción actualiza su marca local. Shadow conservará el cambio pendiente para el siguiente intento.

Resultado en destino normal

  1. Busca por las columnas clave mediante un UPDATE parametrizado.
  2. Si el UPDATE afecta una fila, se considera actualización.
  3. Si no existe la clave, ejecuta INSERT.
  4. Solo después del commit exitoso se actualiza el estado local de ese destino.

9. Modo HISTORICO

Cuando DEST_N_HISTORICO=true, MCAAS - DES conserva la detección de cambios, pero no intenta actualizar la fila existente. Cada versión nueva o modificada genera un INSERT.

Ejemplo: un cliente se extrae a las 10:00. A las 10:15 cambia su nombre. El destino normal queda con el nombre nuevo; el destino histórico recibe una segunda fila con la versión nueva.

La tabla histórica debe estar diseñada para aceptar múltiples filas con las mismas columnas clave de negocio. Es habitual añadir en la propia tabla un ID autonumérico o una marca temporal generada por la base. MCAAS - DES no agrega columnas que no existan en el SELECT.

Semántica de entrega: el modo histórico es de tipo at-least-once. En una caída extremadamente puntual entre el commit remoto y el guardado del estado local, el siguiente arranque podría repetir ese INSERT. Si la ausencia absoluta de duplicados es crítica, diseñe el destino con una clave de idempotencia/versionado.

10. Errores, reinicio y estado persistente

Fallo transitorio

Un error de conexión o escritura se registra y se vuelve a intentar. Los fallos de un destino no impiden que otros destinos ya procesados conserven su estado correcto.

Fallo fatal del ciclo

Si falla la extracción origen o el ciclo principal, el motor desconecta, espera AUTO_RESTART_DELAY_MS y vuelve a iniciar conexiones. Además, la tarea de Windows tiene política de reinicio si el proceso termina.

Error persistente

Si se alcanzan FAILURE_THRESHOLD fallos dentro de FAILURE_WINDOW_HOURS:

  1. Se escribe state/persistent-error.json.
  2. Se muestra el mensaje "Error persistente en curso; requiere atención".
  3. Se intenta enviar un correo por Gmail API.
  4. La aplicación permanece viva, pero pausa extracción y envío.
  5. La pausa continúa aunque se reinicie Windows.

Cómo reanudar

Primero corrija la causa. Después ejecute:

mcaas-des.exe --clear-persistent-error --config "C:\ProgramData\MCAAS-DES\.env"

El servicio detectará la liberación en su siguiente verificación y reanudará la sincronización.

12. Activación de Gmail API

MCAAS - DES usa OAuth 2.0 y el scope https://www.googleapis.com/auth/gmail.send. No necesita leer la bandeja.

12.1 Google Cloud

  1. Cree o seleccione un proyecto en Google Cloud Console.
  2. Abra APIs y servicios y habilite Gmail API.
  3. En Google Auth Platform configure Branding, Audience y Data Access.
  4. Si pertenece a Google Workspace y el proyecto será solo interno, use audiencia Internal cuando esté disponible. Si es External, agregue la cuenta emisora como usuario de prueba mientras desarrolla.
  5. Cree un OAuth Client ID de tipo Web application.
  6. Agregue como redirect URI autorizado: http://localhost:53682/oauth2callback.

12.2 Obtener refresh token

En una PC de desarrollo con Node instalado, copie .env.example a .env y cargue:

GMAIL_CLIENT_ID=...
GMAIL_CLIENT_SECRET=...
GMAIL_REDIRECT_URI=http://localhost:53682/oauth2callback

Luego ejecute:

node scripts/generate-gmail-token.mjs --config .env

Abra la URL mostrada, autorice la cuenta que enviará los avisos y copie el refresh token a:

GMAIL_ENABLED=true
GMAIL_REFRESH_TOKEN=...
GMAIL_FROM=alertas@tu-dominio.com
GMAIL_ALERT_TO=soporte@tu-dominio.com

12.3 Producción

Importante: Google documenta que, para apps External en estado Testing, los refresh tokens pueden caducar después de 7 días. Para una operación 24/7, use un proyecto/estado de publicación apropiado para producción o una configuración Internal de Workspace cuando corresponda.

Referencias oficiales consultadas: Google Workspace Gmail API - Node.js quickstart, server-side authorization y sending messages; Google OAuth production readiness. Las políticas de OAuth pueden cambiar, por lo que deben revisarse antes de un despliegue productivo.

15. Instalación en un servidor Windows de CONTPAQi

Opción A: carpeta de release + PowerShell

  1. Compile MCAAS - DES en una PC de desarrollo.
  2. Copie MCAAS-DES-Windows-x64.zip al servidor.
  3. Extraiga la carpeta en una ubicación temporal.
  4. Abra PowerShell como Administrador.
  5. Ejecute:
powershell -ExecutionPolicy Bypass -File .\install.ps1

El instalador copia el binario a C:\Program Files\MCAAS-DES y crea la configuración/estado en C:\ProgramData\MCAAS-DES.

Configurar antes del arranque

  1. Edite C:\ProgramData\MCAAS-DES\.env.
  2. Edite C:\ProgramData\MCAAS-DES\scripts\extraction.sql.
  3. Use un usuario de lectura para la base CONTPAQi.
  4. Configure 1 a 10 destinos.
  5. Si Aiven exige TLS, configure SSL y, cuando aplique, el archivo CA.

Validar

"C:\Program Files\MCAAS-DES\mcaas-des.exe" --validate-config --config "C:\ProgramData\MCAAS-DES\.env"
"C:\Program Files\MCAAS-DES\mcaas-des.exe" --check-connections --config "C:\ProgramData\MCAAS-DES\.env"
"C:\Program Files\MCAAS-DES\mcaas-des.exe" --run-once --config "C:\ProgramData\MCAAS-DES\.env"

Activar 24/7

Ejecute Start-MCAAS-DES.bat como Administrador o inicie la tarea MCAAS-DES Core desde Task Scheduler. La tarea ya está configurada para arrancar con Windows.

Terminal: al iniciar sesión se abre el monitor. Si alguien lo cierra, el core permanece ejecutándose en segundo plano. En un servidor sin sesión interactiva el core sigue funcionando, aunque naturalmente no habrá una ventana visible hasta que un usuario inicie sesión.

Opción B: Setup.exe

Si compiló el instalador Inno Setup, ejecute MCAAS-DES-Setup-1.0.0.exe como Administrador y complete los mismos pasos de configuración/validación.

16. Operación diaria y recuperación

Comprobaciones periódicas

  • El log diario contiene heartbeat reciente.
  • No existe error persistente activo.
  • El espacio libre en disco es suficiente.
  • Los destinos reciben filas nuevas/modificadas.
  • El refresh token de Gmail sigue válido.

Después de cambiar el SQL

Ejecute --validate-config, luego --run-once. Si cambia la tabla destino o las columnas clave, MCAAS - DES crea un stream de estado distinto, por lo que puede producir una resincronización.

Después de cambiar credenciales

Guarde el .env, pruebe --check-connections y, si había un error persistente, ejecute --clear-persistent-error.

Respaldos recomendados

  • .env, protegido como secreto.
  • scripts/extraction.sql.
  • state/, si desea conservar exactamente las huellas ya enviadas.

17. Seguridad recomendada

  • Use un usuario de solo lectura en la base origen.
  • Use usuarios de escritura limitados a las tablas necesarias en destinos.
  • No reutilice cuentas administrativas de SQL Server/Aiven.
  • Proteja C:\ProgramData\MCAAS-DES\.env con permisos NTFS restringidos.
  • No incluya el .env real en Git, ZIP de soporte ni correo.
  • Use TLS para bases remotas.
  • Evite SSL_REJECT_UNAUTHORIZED=false en producción salvo que el proveedor/arquitectura lo requiera y el riesgo haya sido aceptado.
  • Rote contraseñas y refresh tokens cuando cambie el personal responsable.
  • Los logs de banderas no contienen valores, pero siguen siendo metadatos operativos; protéjalos.

18. Límites y supuestos

TemaComportamiento actual
Tiempo realPolling configurable, no CDC/binlog nativo. El mínimo práctico depende del tamaño del SELECT y de la red.
DeletesNo propaga eliminaciones de la base origen.
DDLNo crea ni migra tablas destino.
Esquemas distintosPuede sobrescribir la tabla por destino con DEST_N_TARGET_TABLE, pero las columnas deben corresponder.
Claves duplicadasSe consideran un error de extracción porque impiden identificar una fila de forma estable.
HistóricoAt-least-once; una caída en la ventana commit remoto/estado local puede producir duplicado.
VolumenEl estado local es JSON. Para datasets de millones de filas o cargas masivas continuas conviene evolucionar el estado a SQLite/LevelDB o usar watermark/CDC.
Cambios de schemaSi el SELECT agrega/quita columnas, los hashes cambian y los destinos deben aceptar el nuevo schema.
